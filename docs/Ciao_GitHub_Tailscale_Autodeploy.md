# ciao — GitHub Auto Deploy via Tailscale

## Goal

Add optional GitHub CI/CD to the normal ciao deploy flow without adding a ciao cloud, public SSH, webhook server, or permanent remote control plane.

The intended UX is:

```bash
ciao deploy home
```

On the first successful deploy, when ciao detects a GitHub repository:

```text
✓ deployed successfully
✓ GitHub repository detected: luca/my-api
✓ Tailscale detected on target: home

Enable automatic deploys from GitHub on push to `main`? [Y/n]
```

If accepted:

```text
✓ GitHub authenticated
✓ Tailscale CI identity configured
✓ dedicated deploy key created
✓ GitHub Actions configured
✓ auto-deploy enabled

Future pushes to `main` will deploy automatically.
```

After setup:

```text
git push
   ↓
GitHub Actions
   ↓
ephemeral Tailscale node
   ↓
private tailnet
   ↓
SSH
   ↓
ciao deploy
   ↓
build → healthcheck → activate
```

No public SSH port is required.

---

## 1. Product rule

GitHub integration must remain an **optional extension of `ciao deploy`**.

Do not create a separate deployment engine.

Both manual and CI deployments must execute the same core:

```text
                    ciao_core
                    /           \
                   /             \
          interactive CLI      CI mode
                   \             /
                    \           /
                  deploy engine
```

The workflow must not reimplement upload, release creation, build, healthcheck, activation, rollback, or service lifecycle.

---

## 2. Why Tailscale

ciao should use Tailscale as the supported private-network path for GitHub-hosted runners.

Do not implement Cloudflare CI connectivity in this scope.

Tailscale provides:

```text
GitHub-hosted runner
        ↓
temporary authenticated tailnet node
        ↓
private host
```

This is particularly appropriate for homeservers, Mac minis, private VPSes, and machines behind NAT/CGNAT.

---

## 3. Tailscale network + normal SSH

Do **not** require Tailscale SSH for ciao CI.

Use:

```text
Tailscale → private network connectivity
OpenSSH   → remote authentication and command execution
```

Architecture:

```text
GitHub runner
     │
     │ Tailscale
     ▼
private host address
     │
     │ standard SSH
     ▼
ciao target
```

Reasons:

```text
same SSH transport used by normal ciao
works with existing remote deployment code
no second SSH implementation
no Tailscale SSH-specific policy model
dedicated CI key can be revoked independently
works with Linux and macOS
```

The target can therefore be Linux x86_64, Linux arm64, macOS Intel, or macOS Apple Silicon.

Apple Silicon remains a first-class target.

---

## 4. GitHub Actions authentication to Tailscale

Preferred mechanism:

> **Tailscale workload identity federation using GitHub Actions OIDC.**

Do not use a long-lived Tailscale auth key in the repository when workload identity federation is available.

Conceptually:

```text
GitHub Actions OIDC token
          ↓
Tailscale federated identity
          ↓
short-lived access
          ↓
ephemeral CI node
```

Required workflow permission:

```yaml
permissions:
  contents: read
  id-token: write
```

The generated workflow should use the official Tailscale GitHub Action.

Conceptually:

```yaml
- name: Connect Tailscale
  uses: tailscale/github-action@v4
  with:
    oauth-client-id: ${{ vars.TS_OAUTH_CLIENT_ID }}
    audience: ${{ vars.TS_AUDIENCE }}
    tags: tag:ciao-ci

- name: Install Ciao
  run: |
    # download the pinned Ciao release for the GitHub runner
    # verify checksums.txt before installing it in $HOME/.local/bin
```

Ciao generates this workflow from the detected project. It includes the
runtime and app type, downloads a pinned Linux Ciao binary, and verifies its
checksum. It does not install Rust unless a separate project step needs Rust.

## 5. One-time Tailscale bootstrap

Being logged into the local Tailscale client does not automatically give ciao tailnet admin API permissions.

For the first repository that enables GitHub auto-deploy, allow one short interactive bootstrap.

Desired flow:

```text
Tailscale is connected, but ciao needs one-time admin permission
to configure GitHub workload identity.

Open Tailscale setup page? [Y/n]
```

The simplest v1 implementation may request a temporary Tailscale API access token generated by the user. Ciao uses it only for the one-time policy and identity bootstrap; it is not copied into the generated workflow or Ciao state. If the GitHub repository is configured for repeated setup, the operator may rotate or revoke it after setup.

Example:

```text
Paste temporary Tailscale admin token:
> ********

This token will be used only for setup and will not be stored.
```

Rules:

```text
never write the bootstrap token to disk
never commit it
never upload it to GitHub
never log it
drop it from memory after setup
```

Use it only to configure the permanent secretless CI identity.

A delegated OAuth flow can be a later improvement; do not block v1 on it.

---

## 6. Federated identity scope

Create one federated identity per linked repository unless a clearly simpler safe reuse strategy exists.

Identity:

```text
description: ciao GitHub CI — owner/repo
issuer: GitHub Actions OIDC
tag: tag:ciao-ci
```

Restrict the identity as tightly as practical.

At minimum constrain:

```text
repository / repository_id
branch ref
```

Recommended conceptual matching:

```text
repository_id = exact GitHub repository ID
ref           = refs/heads/main
```

Optionally also constrain workflow_ref, event_name, and repository_owner_id.

Never create a rule equivalent to:

```text
all GitHub Actions → tailnet
```

---

## 7. Tailscale tag and ACL scope

Use a dedicated CI identity:

```text
tag:ciao-ci
```

The tag exists only to identify ephemeral ciao GitHub runners.

The CI tag should be granted only the network access needed for deployment:

```text
tag:ciao-ci
      ↓
target host
      ↓
TCP 22
```

Do not grant unrestricted tailnet access.

The first setup also ensures that `tag:ciao-ci` is owned by
`autogroup:admin` when the policy does not define that tag yet. Existing tag
owners are preserved. This is required because the ephemeral GitHub runner
must be allowed to claim the CI tag; it does not grant the tag access to any
other host beyond the explicit TCP/22 grant.

---

## 8. Tailnet policy changes

Policy mutation is security-sensitive.

ciao must:

```text
1. fetch current policy
2. preserve all existing rules
3. compute the minimal required patch
4. validate the resulting policy
5. show a concise diff
6. ask permission before applying
7. apply through the Tailscale API
8. verify connectivity
```

Never replace the user's policy with a ciao template.

Never silently loosen unrelated rules.

If the policy cannot be safely patched:

```text
stop
show the exact required rule
let the user apply it manually
continue verification afterwards
```

Safety is more important than literal zero prompts.

Do not build a proprietary GitHub account system.

```text

create/update Actions secrets

write the generated workflow locally
```

## 11. Target Tailscale detection

Inspect Tailscale on the deployment target through the already-working ciao SSH connection.

The setup is guided. Ciao reuses an installed client and installs it through
the native Linux package path or Homebrew on macOS when it is missing. If the
target is not connected, Ciao starts `tailscale up` as a bounded background
operation, extracts the official login URL, opens it in the local browser and
waits for the target to report `BackendState=Running`. A user never has to
type `tailscale up`; if the browser launcher is unavailable, Ciao prints the
validated Tailscale URL as a fallback. The same flow is used locally when the
configured SSH address is a Tailscale address and the local client is not
connected.

Detect:

```text
tailscale binary
connection state
tailnet membership
Tailscale IPv4
MagicDNS hostname if available
```

Conceptually:

```bash
tailscale status --json
```

Persist only non-secret target addressing metadata.

Preferred CI target:

```text
MagicDNS hostname
```

Fallback:

```text
Tailscale IP
```

The target must not depend on a public IP.

---

## 12. Dedicated SSH deploy identity

Create a dedicated SSH key pair for GitHub CI.

Do not reuse the developer's personal private key for CI. The normal manual
host link may use an existing user key or the explicit guided local bootstrap;
CI still receives only its own dedicated key.

Recommended:

```text
Ed25519
one key per repository + target
no passphrase for non-interactive CI
```

Lifecycle:

```text
generate locally
↓
install public key on target
↓
store private key as GitHub Actions secret
↓
delete temporary local private key
```

GitHub secret:

```text
CIAO_SSH_KEY
```

Where practical, restrict the authorized key by disabling unrelated forwarding features without breaking ciao deployment.

---

## 13. SSH host verification

Do not disable host-key checking in CI.

Never generate:

```text
StrictHostKeyChecking=no
```

During setup, ciao already has a trusted SSH connection to the target. It
copies the matching entry from the local OpenSSH `known_hosts` file, using the
configured SSH host as the source and the Tailscale name as the CI alias. It
deliberately does not run unauthenticated `ssh-keyscan`.

Store that exact trusted known-hosts entry in GitHub:

```text
CIAO_SSH_KNOWN_HOSTS
```

The workflow reconstructs `~/.ssh/known_hosts` before deployment.

## 14. GitHub repository configuration

Secrets:

```text
CIAO_SSH_KEY
CIAO_SSH_KNOWN_HOSTS
```

Variables:

```text
CIAO_HOST
CIAO_USER
CIAO_APP
TS_OAUTH_CLIENT_ID
TS_AUDIENCE
```

`TS_OAUTH_CLIENT_ID` and `TS_AUDIENCE` are the public identifiers returned by
the Tailscale federated identity. The generated workflow uses them as Actions
variables; they are not long-lived secrets. The CI identity itself must have
the writable `auth_keys` scope required by the official Tailscale action.

Use secrets only for sensitive material.

Never place private keys directly inside workflow YAML.

## 15. Generated GitHub workflow

Create:

```text
.github/workflows/ciao-deploy.yml
```

Keep it very small.

Conceptual structure:

```yaml
name: ciao Deploy

on:
  push:
    branches:
      - main

permissions:
  contents: read
  id-token: write

concurrency:
  group: ciao-production
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Connect Tailscale
        uses: tailscale/github-action@v4
        with:
          oauth-client-id: ${{ vars.TS_OAUTH_CLIENT_ID }}
          audience: ${{ vars.TS_AUDIENCE }}
          tags: tag:ciao-ci
          ping: ${{ vars.CIAO_HOST }}

      - name: Install ciao
        run: |
          # generated workflow downloads the pinned Ciao release asset
          # and verifies checksums.txt

      - name: Configure SSH
        env:
          CIAO_SSH_KEY: ${{ secrets.CIAO_SSH_KEY }}
          CIAO_SSH_KNOWN_HOSTS: ${{ secrets.CIAO_SSH_KNOWN_HOSTS }}
        run: |
          # write key and known_hosts with safe permissions

      - name: Deploy
        env:
          CIAO_HOST: ${{ vars.CIAO_HOST }}
          CIAO_USER: ${{ vars.CIAO_USER }}
          CIAO_APP: ${{ vars.CIAO_APP }}
        run: ciao deploy --ci --path . ciao-target
```

Final syntax must match the actual CLI.

Do not create a CI-only deploy implementation.

---

## 16. Pin ciao in CI

Do not install arbitrary `latest` on every deploy.

The generated workflow should pin a compatible ciao release, normally the current local version at setup time.

Upgrade should be explicit.

This prevents an unrelated ciao release from unexpectedly breaking production CI.

---

## 17. CI mode

Add a non-interactive mode:

```bash
ciao deploy --ci
```

Requirements:

```text
no prompts
deterministic exit codes
machine-readable errors
same DeployEngine as manual deploy
no dependency on developer ~/.config/ciao
```

Target metadata comes from workflow variables/environment.

---

## 18. Deploy concurrency

Prevent two GitHub pushes from deploying simultaneously.

Use GitHub Actions concurrency and also a remote deployment lock.

Conceptual lock:

```text
/var/lib/ciao/apps/myapp/deploy.lock
```

with an equivalent macOS path.

Concurrent deploys must never corrupt `current`.

## 25. Implementation sequence

Implement in this order unless the current repository makes a small variation clearly simpler.

### Step 1 — GitHub detection

Implement:

```text
detect .git
read origin
recognize GitHub
extract owner/repo
query repository metadata
detect default branch
```

Test HTTPS remote, SSH remote, non-GitHub remote, missing remote, and renamed default branch.

### Step 2 — GitHub CLI integration

Implement:

```text
gh availability detection
gh auth status
guided gh auth login
permission verification
GitHub API wrapper
```

Do not implement custom OAuth yet.

### Step 3 — Tailscale target detection

Through existing ciao SSH transport:

```text
detect tailscale
read status JSON
extract Tailscale IP
extract MagicDNS name
verify connected
```

Test Linux and macOS Apple Silicon.

### Step 4 — CI SSH identity

Implement:

```text
generate Ed25519 key
install public key
capture known_hosts
store private key in GitHub secret
delete temporary local key
```

### Step 5 — Tailscale workload identity bootstrap

Implement:

```text
temporary admin token input
Tailscale API client
ensure tag:ciao-ci
create repository-scoped federated identity
minimal policy access
discard bootstrap token
```

### Step 6 — Safe policy patch

Implement:

```text
fetch policy
parse/preserve
compute minimal patch
validate
preview diff
apply
verify
```

If safe patching cannot be guaranteed, stop and request a manual policy edit.

### Step 7 — GitHub repository configuration

Configure automatically:

```text
CIAO_SSH_KEY
CIAO_SSH_KNOWN_HOSTS
CIAO_HOST
CIAO_USER
CIAO_APP
TS_OAUTH_CLIENT_ID
TS_AUDIENCE
```

### Step 8 — Workflow generator

Generate `.github/workflows/ciao-deploy.yml` with:

```text
push branch filter
contents: read
id-token: write
official Tailscale action
pinned ciao version
SSH setup
ciao deploy --ci
concurrency guard
```

Do not auto-commit or auto-push unless explicitly requested.

### Step 9 — CI mode

Make `ciao deploy --ci` work in a clean GitHub runner with no developer ciao config.

It must use the same deploy engine as manual deployment.

### Step 10 — Integration tests

Test:

```text
GitHub workflow → Tailscale → SSH → deploy
Linux target
macOS Apple Silicon target
failed build
failed healthcheck
second deploy
concurrent deploy attempt
rollback after CI deploy
invalid SSH host key
Tailscale unavailable
```

## 26. Failure behavior

Failures must be actionable.

Examples:

```text
Ciao could not install or authenticate Tailscale on `home`.
Automatic GitHub deploy requires a connected Tailscale target.
Manual ciao deploy remains available; rerun setup after fixing the package
manager, sudo permission or browser sign-in.
```

```text
GitHub is not authenticated.
Run: gh auth login
```

```text
ciao could not safely patch the existing Tailscale policy.
No changes were applied.
Required access: tag:ciao-ci → home:22
```

```text
GitHub workflow connected to Tailscale but SSH verification failed.
Production was not modified.
```

## 27. Security invariants

Never violate these:

```text
no public SSH required
no ciao remote admin daemon
no long-lived Tailscale auth key in GitHub
no developer personal SSH key in GitHub
no StrictHostKeyChecking=no
no stored Tailscale bootstrap token
no broad all-tailnet CI access
no destructive policy replacement
```

Prefer:

```text
GitHub OIDC
ephemeral Tailscale nodes
repository-scoped trust
dedicated SSH deploy key
exact SSH host verification
minimal network grants
```

## 30. Definition of done

The feature is complete when this works:

```bash
cd my-api
ciao deploy home
```

User accepts:

```text
Enable GitHub auto-deploy? yes
```

ciao configures the integration.

Then:

```bash
git add .
git commit -m "change"
git push
```

causes:

```text
GitHub Actions
→ ephemeral Tailscale connection
→ private SSH connection
→ ciao deployment
→ successful healthcheck
→ atomic activation
```

with:

```text
no public SSH
no manual workflow creation
no personal SSH key uploaded
no permanent CI node
no ciao daemon on the server
```

The guiding principle remains:

> **Ship apps. Skip the ops.**
